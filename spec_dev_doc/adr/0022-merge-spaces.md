# ADR-0022 合并空间

> 状态：已采纳 · 2026-09-27 · ADR-0021 候选中推迟的「合并空间」；补充 08 §2.5 空间卡片 ⋯ 菜单、01 §3.12 审计动作。

## 背景

空间多了以后，常见的整理需求不是删除，而是「这两个空间其实是一回事」：一个产品先后建了两个空间、一门课拆成了几块。现在只能逐篇把记录移到另一个空间（批量移动只管记录、不管任务、不保留目录），源空间里的任务、目录层级、成员都得手工重建。

## 决定

1. **接口**（REQ-SPACE-013 · 014）：`POST /spaces/:id/merge { into, dryRun? }`，把 `:id`（源 A）整体并入 `into`（目标 B）。返回 `{ preview: { entries, tasks, members, visibilityWidened, from, into }, into? }`；`dryRun` 只校验与预览，不写库。
2. **权限与前置**：对 A 要求 `space.delete`（工作区 owner / admin，因为合并后 A 被删），对 B 要求 `space.manage`，都经 `can()`，不新增动作。A = B → 422；任一方是个人空间 → 403；B 已归档 → 403（只读）；A 已归档可以合并。事务内重新校验一次。
3. **搬什么**：
   - 记录与任务整体改 `space_id`，id 不变，评论 / 附件 / 关联 / 标签 / 收藏 / 历史快照都跟着走；A 回收站里的记录 / 任务一起搬，在 B 里仍可恢复。
   - 目录：A 的顶层页（在目录中的）按原顺序追加到 B 顶层末尾，子页层级不变；不在目录里的仍不在目录。B 的末尾键把回收站里的也算上，避免恢复后与新键重复。
   - 任务：每个状态列里 A 的任务按原顺序排到 B 原有任务之后（重排 `sort_key`，不与 B 交错）。
   - **不改记录 / 任务的 `updated_at`**：合并不是内容编辑，不打乱「最近更新」，也不让打开着的页面保存时撞 `ifUpdatedAt`。
4. **成员**：A 的显式成员并入 B，角色取两边较高者（A 里的角色已按工作区角色封顶，guest 至多 viewer）。原来能看到 A 内容的人合并后仍能看到。
5. **可见性**：A 仅成员、B 全员可见时，A 的内容会对全工作区可见。不拦截，`visibilityWidened` 由确认界面单独警告。
6. **源空间**：成空壳后软删进回收站（30 天后 gc 清除），恢复出来也只是空壳，内容不自动搬回。审计新增 `space.merged`（meta：源名 / slug、目标、记录 / 任务 / 成员数、是否扩大可见范围；迁移 0018 重建 `audit_log_action_ck`）。
7. **界面**（REQ-SPACE-015）：空间卡片 ⋯「合并到…」（工作区 owner / admin），对话框选目标（只列本人管理的、未归档、非个人空间）→ 选中即 dryRun，写明记录 / 任务 / 成员数与可见性警告 → 「合并」。完成后 Toast 可直接打开目标空间。
8. 提交后对 A、B 各广播一次 `entry.access_changed`，collab 按当前数据重新 `can()`。

## 候选与否决

- **不并入成员**：A 里「本空间可见」的记录并入后，原来能看的人就看不到了，等于悄悄收回权限——否决。
- **可见性扩大时直接拒绝**：用户整理空间的常见路径就是把私有的并进公共的；拒绝只会逼他先改 B 的可见性，风险一样。选择警告而不是拒绝。
- **在 B 新建「A」父页挂整棵目录**：会凭空多一篇空记录，且与「不产生新内容」的直觉不符；选追加到顶层末尾。
- **合并后彻底删除或归档 A**：彻底删除不可追查；归档留下一堆空壳。软删进回收站与现有删除路径一致。
- **提供「撤销合并」**：需要记录每一行的原空间与原顺序键，复杂度高；以 dryRun 预览 + 确认 + 审计替代。
